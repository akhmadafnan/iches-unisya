# 21K-06 — OWNER-LOCKED Dev Demo Users: @iches.test and Shared Local Password

> **28 October 2026 · DEV_FIXTURES_POLICY_LOCKED / ICH-S0-03 NOT YET GO.** The owner explicitly requested easy development: test/demo user emails end with **`@iches.test`** and, when a password-based development login is available, **all demo passwords are the literal `password`**. These are intentionally predictable credentials **only for local synthetic test users**. Do not interpret this as production authentication, permission to add passwords to all participants, or authorization for new source edits/migrations.

## Practical implementation rules for Codex

1. **Synthetic seed accounts:** use predictable, role-descriptive emails such as `admin@iches.test`, `reviewer@iches.test`, `presenter@iches.test`, `participant@iches.test` only when the corresponding role and permitted permissions exist. `.test` addresses are for development/testing and must never be treated as real external delivery destinations. No real names, official cohosts, passwords or addresses of actual participants in seeds.
2. **Development password convention:** where demo accounts support a password-based login, use the shared **`password`** and store **only a secure hash** (Laravel `Hash::make('password')`), never a plaintext password in `users.password`. All local dummy accounts that have a password use the same convention. Do **not** use this as a production password, for root MySQL, or as a global authentication bypass.
3. **Existing foundation fact:** the merged S0-02 `users` table has **no `password` column**. The approved attendee/participant login policy remains **passwordless Email OTP / Magic Link**. Merely specifying the demo credential does not create a usable password login. If a local-only developer/demo login is genuinely needed for faster UI testing in S0-03, Codex must implement it **explicitly and gated to local/testing** without changing attendee production auth policy; any nullable password field must be justified and created by a new forward migration under the named S0-03 GO. Otherwise keep participants passwordless and allow local OTP/Magic Link via log / local inbox.
4. **Simple, repeatable seed:** Codex should make fixture creation idempotent (`updateOrCreate` or equivalent by normalized email) and scope actual roles to an explicitly synthetic event/institution. Existing domain migrations and role audit history must not be reset for re-seeding. Use controlled seeder execution, no `migrate:fresh`/DROP/TRUNCATE. Prefer a dedicated dev-demo seeder that does not run automatically on CI or production.
5. **One simple hard stop:** demo seed and any demo-only login must require `APP_ENV=local` or a genuinely isolated test environment **and** an explicit development flag (e.g. `ICHES_DEMO_MODE=true` in ignored local `.env`). Production/staging must not enable this path; if enabled unexpectedly there, fail closed. Routes and seeded weak credentials must not be accessible in real deployment.
6. **Before production release:** disable/remove demo login/seed flag and demo accounts, use a separately provisioned production database and proper mail delivery/OTP, verify default passwords cannot authenticate, then perform ordinary access, secret and security tests. Do not indiscriminately erase the owner's development schema now or infer approval for automatic deletion.
